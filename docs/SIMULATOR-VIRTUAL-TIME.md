# Deterministic offline trigger simulation

Event Intelligence already supports isolated `simulateTrigger()` runs over a
canonical Pattern AST v2 definition. The `startAt` option controls the
**processing-time** clock, including runs with zero incoming events. No source
polling, wake continuation, registry write or production event store is used.

```js
import { simulateTrigger } from './scripts/lib/trigger-inspector.mjs';

// Use your canonical definition from the planner.
const report = await simulateTrigger({
  definition,
  events: [],
  startAt: '2026-10-10T09:00:00.000Z',
  until: '2026-10-10T10:00:00.000Z',
});
console.log(report.evaluatedUntil, report.inspection.why);
```

The standalone MCP `trigger_simulate` tool also accepts `startAt` as an
optional offset-aware ISO timestamp. Both the public JavaScript API and MCP
reject timezone-less values and impossible calendar dates (such as February 30)
instead of accepting locale-dependent `Date.parse()` normalization. The simulation clock starts at `startAt`
when supplied, otherwise it retains the existing initial event-time anchor
(and historically falls back to actual time when no events are provided).
Processing time never moves backwards; input events may be older than the
starting clock without silently rewriting their event-time timestamps.
`until` cannot precede an explicit `startAt`.

All timestamps generated by the in-memory simulation store now use the same
injected clock for repeatable state and deadline records. This does not alter
live PostgreSQL/JSONL storage or the production scheduler.

Errors are machine-readable:
- `EVENT_SIMULATION_START_TIME_INVALID`
- `EVENT_SIMULATION_END_TIME_INVALID`
- `EVENT_SIMULATION_TIME_RANGE_INVALID`

This is a focused part of [#46](https://github.com/sarooo17/event-intelligence/issues/46),
not a substitute for multi-host clean-room testing or full CEP formal proof.
