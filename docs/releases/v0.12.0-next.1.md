## What's newly included since `0.12.0-next.0`

- **Runtime-neutral SDK completeness**: canonical `createEventIntelligence()`
  embedded and headless conformance, no vendor-specific runtime/session policy.
  The host still owns MCP credentials, tenant authz, approvals and durable
  continuation dispatch.
- **Safer wake receipt contract (breaking)**: successful delivery requires
  an actual host-issued `runtimeReceiptId`, not a fabricated void-delivery
  success; approval evidence comes from the current host `control()`
  decision, not stale confirmation aliases.
- **Explainability**: versioned, bounded fail-closed causal inspection, source
  gap/unknown fidelity, strict PostgreSQL16 inspection including 100k-tier
  candidate limits. A signed test-source frontier is not a third-party
  provider completeness certification. [#48](https://github.com/sarooo17/event-intelligence/issues/48).
- **Optional semantic evaluation**: host-provided evaluator, bounded
  per-trigger/batch call/token/worst-case **estimated cost** reservations,
  PG16 concurrency/restart/unknown-outcome denial, tenant-scoped caches.
  EI does not guarantee the provider's final bill or remote stop-billing.
  [#49](https://github.com/sarooo17/event-intelligence/issues/49).
- **Lossless source/audit retention contract**: no automatic physical pruning
  of source occurrence history, dedup identities, audit or durable wake
  receipts. Operator-only bounded PostgreSQL source/audit/match/wake
  integrity preflight checks (including SQL lock timeout and byte guards)
  and safe terminal-duplicate-only history compaction, with real PG16
  cross-pool, restart and injected corruption evidence.
  **Storage will grow indefinitely** until the operator manages capacity or
  a separately reviewed pruning/floor protocol exists. [#47](https://github.com/sarooo17/event-intelligence/issues/47),
  [PR #378](https://github.com/sarooo17/event-intelligence/pull/378).
- **Release classification**: nine mandatory SDK-v1 correctness/readiness
  gates remain manually blocked in the stable-v1 ledger; six external
  production certifications are optional for the generic SDK but cannot
  be claimed as complete. No stable tag, MCP Registry prerelease entry or
  automatic consumer upgrades.

## Compatibility / upgrade boundaries

- Node `>=22`, ESM, official
  `@modelcontextprotocol/server@2.0.0`, PostgreSQL driver `pg@8.16.3`.
- Canonical Pattern AST v2, trigger protocol `0.2.0`,
  trigger schema `trigger.v0.2`, PostgreSQL physical schema marker 1
  and candidate Pattern-v2 signature identity marker 2.
- Hosts must return a durable `runtimeReceiptId` and implement host
  receipt lookup/reconciliation for real crash replay; `control(request)`
  replaces obsolete `authorize()`, and stale approval aliases are refused.
- **No silent shared-DB mixed-version rollout:** stop all old workers,
  snapshot and verify original state, check the stored signature marker,
  then run the new candidate on isolated state. Incompatible populated
  stores fail closed and require operator-controlled backup/reset/restore
  and verified authoritative replay. A package install does not migrate
  user/tenant DB state or host deployment.
- Experimental MCP Events provider profile and incomplete source history
  must not be misrepresented as finalized remote event-time completeness.
- See the [version-specific compatibility and migration matrix](
  0.12.0-next.1-compatibility.md) and
  [PostgreSQL v1 no-prune contract](
  ../POSTGRES-V1-NO-PRUNE-RETENTION-CONTRACT.md).
