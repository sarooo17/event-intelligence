# MCP Event Intelligence v0.3.0

This release turns Event Intelligence from a durable event engine with a management surface into a substantially easier primitive for agent runtimes.

## Agent-first trigger creation

Hosts and MCP clients can now submit an agent-friendly trigger plan instead of constructing the internal composite-trigger DSL manually.

The planner:
- resolves event names against the sources that are actually available;
- fills source/server identifiers;
- validates predicate fields against advertised payload schemas;
- supports common `all`, `any`, `sequence` and `count` patterns;
- returns the canonical definition plus the connection IDs required for persistence.

Planning is deterministic and does not invoke another model.

## Continuation contract

A trigger may now persist a first-class continuation instruction describing what the runtime should do after the future condition becomes true. This separates:

- **when to wake** — the trigger condition;
- **what to do after waking** — the continuation contract.

Existing triggers without a continuation remain compatible.

## Activation Envelope

The wire wake remains intentionally small and reference-only.

A host can hydrate the wake into an Activation Envelope containing:
- target runtime information;
- the persisted continuation;
- trigger and match state;
- the matched event evidence;
- event payloads when allowed by the continuation context policy;
- explicit trust labels marking external event evidence as untrusted.

Embedded hosts automatically receive the activation as the second argument to the wake callback, and can reconstruct it later with `hydrateWake(wakeId)`.

## MCP tools

New read-only tools:
- `trigger_plan`
- `wake_hydrate`

`trigger_create` can now accept either the canonical definition or an agent-friendly plan. Mutation controls are unchanged.

## Matching

Numeric field comparisons are now supported through:
- `gt`
- `gte`
- `lt`
- `lte`

## Verification

The release includes end-to-end tests for the intended agent flow:

`plan -> persist -> future event -> match -> lightweight wake -> hydrated activation -> runtime receipt`

The clean-room smoke also now packs and installs the candidate repository artifact so the release candidate itself, rather than a historical published version, is validated.
