# Event Intelligence SDK v1.0.0 — prepared release notes

> **Source candidate, not a publication record.** This file prepares the
> future stable GitHub Release. No stable npm package/tag/Registry version
> exists merely because these notes are checked in. The release is blocked
> until [#41](https://github.com/sarooo17/event-intelligence/issues/41)
> records all nine required, exact-source reviewer signoffs and an
> operator uses the separately gated manual npm publishing workflow.

## Stable SDK surface

- Host-neutral event-condition and targeted-wake SDK, with current
  `package.json#exports` and typed, packed npm consumer contracts;
  no built-in provider OAuth, host policy or agent loop.
- Canonical Pattern AST v2 with temporal/composite/derived-event logic,
  versioned source/trigger contracts, scoped tenant ownership and
  bounded explainability. Unknown upstream completeness never becomes
  fabricated negative certainty.
- Durable PostgreSQL16 multiworker matching/receipts, ledgered
  idempotency, fenced dispatch and crash/restart recovery under the
  separately tested reference-host assumptions.
- Opt-in host-provided semantic evaluator with deterministic prefilters,
  tenant-scoped cache, bounded trigger/batch admission and conservative
  estimated token/cost reservations. No direct provider dependency.
- v1 no-prune source, match, audit and receipt evidence: append-only
  correctness takes precedence over automatic deletion. Index-backed
  scope-local audit-head append avoids the historical full-chain reload
  hot path ([PR #407](https://github.com/sarooo17/event-intelligence/pull/407)).

## Breaking and persistent-state boundaries

- Pre-v1 deprecated `authorize()`/boolean grants, implicit success
  from void delivery acknowledgments, stale approval aliases and old
  non-Pattern trigger formats are **not** preserved as compatibility APIs.
  The host must use `control(request)` for durable writes, return a real
  host-issued `runtimeReceiptId` and be able to reconcile it after a
  crash or ambiguous completion.
- Pattern-v2 signature contract identity is independently versioned
  from the SQL physical schema; mixed old/new workers against a shared
  PostgreSQL store are not automatically safe. Before upgrading a
  populated store: **stop all writers**, verify a complete backup,
  rehearse on an isolated restored clone, check explicit persisted
  markers and reconcile durable host effects. If source replay/receipts
  are insufficient, abort; never silently reset or downgrade.
- Public npm export/type compatibility and all limitations are listed
  in the [exact v1.0.0 compatibility matrix](1.0.0-compatibility.md).
  Node `>=22` and PostgreSQL16 are the current tested baseline.
- Publishing this library changes neither Muffin nor Artemis dependency
  pins or deployed agents. Upgrades require the downstream owner's own
  code/lockfile PR, migration tests and rollout approval.

## Non-guarantees and optional enterprise work

This SDK does not certify a particular independently operated host,
upstream provider's claimed event-time finality, financially settled
OpenAI usage or abort-stops-billing semantics, production PostgreSQL
primary failover/RPO/RTO, immutable off-host WORM archive or global
p99/SLO. It does not guarantee mathematical exactly-once external
side effects without host cooperation and durable receipts.
No-prune can mean **unbounded storage growth**: operators must provision
backup, quota/capacity and explicit monitoring.

The optional, still-open deployment and enterprise certification
workstreams [#317](https://github.com/sarooo17/event-intelligence/issues/317)
and [#376](https://github.com/sarooo17/event-intelligence/issues/376)
are separate from the nine required bounded SDK-v1 correctness gates.

## Publication provenance

Actual release eligibility is checked by
`docs/releases/v1-readiness.json` and
`scripts/evidence/v1-release-readiness.mjs --strict` against the
**exact reviewed source ancestor**, with no intervening non-ledger code
change. Full CI, PostgreSQL16, package clean-room type/exports checks,
security and recovery evidence, operator backup/replay and manual
review are necessary but do not independently grant publication rights.

Only an explicitly confirmed `Publish npm` workflow on `main` can
publish the `1.0.0` package; after its success the release workflow
rechecks strict readiness and may publish to the MCP Registry and
create a GitHub Release. No automatic consumer upgrade occurs.
