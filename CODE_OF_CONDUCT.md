# Code of Conduct

Event Intelligence is an open-source project for dependable, host-neutral
event-driven systems. We want contributions and technical disagreements to be
constructive, evidence-based and welcoming to people of different experience
levels.

## Expected behavior

- Be respectful and patient, including when discussing defects or design decisions.
- Critique ideas, specifications, code and evidence, not contributors.
- Explain technical concerns with reproducible examples when possible.
- Respect privacy: redact credentials, user data, private event payloads and
  customer-specific material from issues, PRs and public discussions.
- Acknowledge uncertainty and correct inaccurate claims, particularly for
  reliability, security and production-certification evidence.

## Unacceptable behavior

Harassment, discrimination, threats, intimidation, personal attacks, sexualized
attention, publishing someone else's private information, deliberate disruption
of collaboration, or retaliation against good-faith reports are not tolerated.

## Scope

This policy applies to the repository, GitHub issues, pull requests, reviews,
discussions and public project spaces where someone represents Event Intelligence.

## Reporting and enforcement

For **non-sensitive** behavior concerns, open an issue explaining that you need
maintainer help with a conduct concern, without naming private details. For a
**confidential** concern, contact a maintainer via a private contact method they
have publicly chosen to provide; if no private route is available, do not put
sensitive testimony or personal data in a public issue. Security vulnerabilities
have their own reporting instructions in [SECURITY.md](SECURITY.md); a security
advisory is **not** a general-purpose confidential conduct inbox.

Maintainers will evaluate reports in context, seek minimal relevant evidence,
limit sharing to people who need to know, and respond proportionately. Possible
actions include a private warning, hiding inappropriate content, closing or
locking a discussion, and temporarily or permanently restricting participation.
Maintainers are also subject to this policy. No fixed response-time or
confidential reporting channel is promised when one is not available.

## Technical disagreement

Architecture, API compatibility, benchmark interpretation and acceptance
criteria can be debated. An issue or PR is not a personal endorsement.
An unsatisfied test or independent-review requirement should remain explicitly
unverified rather than being characterized as a contributor failure.
